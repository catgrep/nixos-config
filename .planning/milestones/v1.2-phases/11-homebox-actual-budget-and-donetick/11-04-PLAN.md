<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub source -> Nix store | `fetchFromGitHub` pins an exact commit/tag with a content hash; nix verifies it, so the trust anchor is the pinned rev, not GitHub's live HEAD |
| Nix store -> world | Everything in `/nix/store` is world-readable; DT_JWT_SECRET must never land there |
| ser8 loopback tcp/2021 | Not yet gateway-exposed in this plan; plan 11-05 adds the tsnet vhost |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-11 | Information Disclosure | DT_JWT_SECRET in the Nix store | high | mitigate | Delivered via `sops.templates."donetick.env"` + `EnvironmentFile`, never a literal Nix string; Task 2's acceptance criteria assert the template references the sops placeholder |
| T-11-12 | Spoofing | Weak or example JWT secret silently accepted | medium | mitigate | Generated via `openssl rand -base64 32`; Donetick's own `validateJWTSecret` additionally rejects anything under 32 characters or matching its weak-secret denylist, crash-looping the unit rather than starting insecurely |
| T-11-13 | Elevation of Privilege | DT_SINGLE_CIRCLE_INSTANCE silently enabled | medium | mitigate | Explicitly never set; Task 2's acceptance criteria grep confirms its absence, since setting it true would strip the join/accept routes plan 11-05's bootstrap requires |
| T-11-SC | Tampering | Go module supply chain (buildGoModule fetching from github.com/donetick/donetick) | high | mitigate | `fetchFromGitHub` pins an exact tag and content hash (nix build fails loudly on any mismatch); `vendorHash` similarly pins every transitive Go dependency's content. Not an npm/pip/cargo install, so the formal Package Legitimacy Gate protocol does not apply, but the same content-addressed-pin discipline is followed |
| T-11-SC-NPM | Tampering | npm supply chain (buildNpmPackage fetching from github.com/donetick/frontend + the npm registry) -- CORRECTED during execution: Donetick's UI is a *second* repository, not part of donetick/donetick, and this plan's original T-11-SC claim of "not an npm/pip/cargo install" was false. See 11-04-SUMMARY.md Deviations for the full discovery | high | mitigate | `fetchFromGitHub` pins the exact `donetick/frontend` commit (traced via the GitHub API to the commit that was HEAD when the real v0.1.79 release build ran) and its content hash. `npmDepsHash` similarly pins the full resolved dependency tree's content, using a vendored, fully-resolved `package-lock.json` (`packages/donetick/frontend-package-lock.json`) committed in this repo rather than fetched at build time, since upstream's own committed lockfile is incomplete (missing resolved/integrity for 65.8% of entries, npm/cli#6301) and is never used as-is by upstream's own release process either. The Package Legitimacy Gate protocol (deviation Rule 3's exclusion) still does not formally apply -- no `npm install <pkg>` command is ever run against a live, unpinned registry state during this build; every dependency resolves against the vendored, content-addressed lockfile |
