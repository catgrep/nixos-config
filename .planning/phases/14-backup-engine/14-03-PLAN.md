<objective>
Build the consumption half of the engine: a generic nightly dump that captures every discovered
database in a portable format, and a generic nightly verification that reads the new snapshot and
proves the databases inside it recover.

Purpose: an atomic snapshot is a complete crash image, but two things it cannot do on its own are
survive a PostgreSQL major-version change and tell you it is intact. The dump answers the first
by riding a portable archive inside every snapshot and every replica. The verification answers
the second within a day, which is well inside the retention window, so a corrupt database is
caught long before it can age out the good copies. Both are discovery-driven with zero
per-service registration, because the failure mode being designed out is a service added later
and silently never verified.

Output: the dump unit, the verification unit and its timer, the shared failure-mail unit, the
nightly manifest and digest, the freshness metrics, and the VM assertions that prove a corrupt
database is actually caught.
</objective>

  The verification job is the largest single artifact in this phase and the place where the
  architecture's central claim is either proven nightly or merely asserted. Build it to prove it.

  **`hosts/ser8/backup/verify.nix`** — `systemd.services.backup-verify`, `Type=oneshot`, running
  as root because it reads every service's state directory, with `onFailure` set to the mail
  template, and a paired `systemd.timers.backup-verify` with `OnCalendar = "03:30"` and
  `Persistent = true`. Half an hour after the snapshot is enough for a steady-state replication
  run and leaves an hour of margin before the nightly upgrade timer; do not move it
  pre-emptively, record the observed durations in the manifest and move it only if a measurement
  demands it.

  `Persistent = true` only works here because the timer stamp directory was added to the
  persisted set in the storage plan — before that change it silently never replayed on this
  host. Say that in the comment, because a persistent timer that quietly does not persist is
  exactly the kind of thing that reads as fine.

  Also declare a tmpfiles rule creating `/persist/var/lib/node-exporter-textfile` mode `0755`
  owned by root. The directory is declared here, next to the only thing that writes to it, and
  the metric exporter is pointed at it from the monitoring module in a later plan. It must be
  under the persisted tree so the metrics survive the boot-time rollback, and outside any home
  directory because the exporter runs with home directories hidden. World-readable is
  deliberate and needs the comment: the exporter only reads, and the files carry timestamps and
  counts rather than anything sensitive.

  Export the interpolated paths of the ZFS tools, `sqlite3`, `pg_restore`, `findmnt`,
  `mktemp`/`install` and the sendmail wrapper into the script's environment; nothing is assumed
  on the path.

  **Sandbox the unit.** It runs as root and that is not negotiable: the snapshot trees preserve
  the live directories' permissions, which means owner-only directories belonging to sixteen
  different service accounts. No single unprivileged user can walk that tree, and inventing one
  that could would mean either relaxing those permissions or granting an equivalent capability —
  both worse than running as root under a tight sandbox. So the shape is root that reads
  everything and writes almost nowhere:

  - `ProtectSystem = "strict"`, making the entire filesystem read-only by default. The job reads
    constantly and writes to exactly two places, so this costs nothing and removes everything.
  - `ReadWritePaths` naming only the manifest directory and the metrics directory. Both must be
    listed — omitting the metrics directory breaks the run at its final step, which is the step
    whose absence the staleness alert then reports, so the failure would be correctly detected
    but confusingly attributed.
  - `PrivateTmp = true` to supply the scratch space the database checks copy into, so no
    host-level scratch path needs to be writable and the scratch is cleaned up by systemd
    regardless of how the run ends.
  - `NoNewPrivileges = true`.
  - A minimal `CapabilityBoundingSet`. The job needs to traverse and read directories it does not
    own, and to issue pool operations for listing, reading snapshot properties and managing
    holds. Start from the smallest set that plausibly covers those, verify it empirically by
    running the unit in the virtual machine, and record the exact set that worked along with what
    each capability in it is for. Do not copy a set from elsewhere and assume it fits.

  One directive to deliberately *not* set, with a comment saying so: `PrivateDevices`. It would
  hide the pool control device the job needs, and the resulting failure looks like a permissions
  problem rather than a namespace one, which is an expensive hour for whoever debugs it.

  **`hosts/ser8/backup/verify.sh`** — strict mode, `umask 0077`, an error trap that names the
  failed operation, and an exit path that is a failure whenever anything it needed was missing.
  The whole file is written fail-closed: absent is a failure, unreadable is a failure,
  unparseable is a failure. Never a skip.

  Steps, in order:

  1. **Find the subject.** The newest daily snapshot of `rpool/safe/persist`, sorted by creation.
     No snapshot at all is a failure. A snapshot older than 26 hours is a failure. That single
     check also catches "the snapshot job never ran" with no extra plumbing.
  2. **Walk the tree.** Enumerate every dataset under `rpool/safe/persist` with its mountpoint;
     resolve a legacy mountpoint to its real target through the mount table. For each, the
     snapshot view is the snapshot subdirectory beneath the dataset's own mountpoint. That path
     is reachable even though the snapshot directory is hidden from listings — hidden removes it
     from directory enumeration, not from the namespace. A dataset whose snapshot view is
     missing is a failure, since the recursive snapshot guarantees the same name on every child.
  3. **Discover databases by kind, not by registry.** Under each snapshot view, find regular
     files matching the SQLite naming conventions, excluding the write-ahead-log and
     shared-memory sidecars. Enumeration and reading are null-delimited end to end so a path
     containing whitespace or a newline cannot split a field, and no discovered path is ever
     evaluated.
  4. **Check each database the way a restore would.** Copy the database and whichever of its two
     sidecars exist into a scratch directory outside the snapshot, then open the copy read-write
     and run the structural check. This is the load-bearing step and it deserves the longest
     comment in the file: a read-only snapshot path cannot host the shared-memory file a
     write-ahead-log database needs, so an in-place check either errors or, if forced to treat
     the file as unchangeable, skips the log entirely and validates a stale image while
     reporting success. Copying out and opening read-write replays the log — which is exactly
     the recovery path this whole design claims — so the check proves the claim instead of
     assuming it. Use the full structural check for databases up to 64 MiB and the faster
     page-level check above that, since two of the databases on this host are around 175 MB;
     record which check was used per file so the evidence is honest. Any result other than the
     single expected success token is a failure. Remove the scratch directory whether the check
     passed or failed.
  5. **Check the dumps that rode inside this snapshot.** List each archive found under the
     snapshot view of the dump directory. A failure to list is a failure of the run.
  6. **Check the replica by existence and freshness only.** Read the newest daily snapshot on
     `backup/persist-replica` and require it to be within 26 hours. Deliberately do not verify
     integrity on the replica: the checksums that make a source-replica integrity divergence
     essentially impossible are already covered by the pool scrub and its existing alert, and
     mounting the replica nightly would add a mount of a deliberately unmounted dataset for no
     new information. Comment that reasoning, because "we only check one side" reads like an
     oversight otherwise.
  7. **Advance the last-verified hold, per dataset, only on a clean result.** Each dataset in the
     tree carries a `zfs hold` tagged `last-verified`. When every database and archive belonging
     to a dataset checked clean in this run, release that dataset's existing hold and place a new
     one on tonight's snapshot of that dataset. When anything belonging to it failed, leave the
     hold exactly where it is.

     The consequence is the whole point and belongs in the comment: a held snapshot cannot be
     destroyed, so the last snapshot that was *proven good* for a given service is structurally
     safe from pruning until a later one is proven good. Retention alone does not give that — a
     thirty-night window happily ages out the last healthy copy while thirty corrupt ones sit on
     top of it. This turns "we would have noticed within a day" into "the good copy is pinned
     until it is replaced by a better one".

     Advance per dataset rather than per run, so one failing service does not pin the whole tree
     and a healthy service is not held back by an unhealthy neighbour.

     Order matters: release-then-place, and treat a failure of either half as a failure of the
     run. Placing before releasing would accumulate holds and pin the entire window; releasing
     without placing would leave a service unprotected, which is worse than either.

     **Known interaction to verify rather than assume.** Pruning destroys snapshots, and a
     destroy against a held snapshot is refused. In normal operation the hold sits on a snapshot
     no more than a day old, far inside the thirty-night window, so pruning never reaches it. The
     pathological case is verification failing for the whole window, at which point the hold pins
     the oldest snapshot and pruning does try to destroy it. Determine in the virtual machine
     whether the pruning run treats that refusal as a fatal error. If it does, that is acceptable
     and must be documented rather than worked around: verification failing for thirty
     consecutive nights *should* produce a loud failure, and the mail it generates is correct
     signal rather than noise. Record the observed behaviour either way.

  8. **Write the manifest**, to `/persist/var/lib/backup-manifests/<YYYY-MM-DD>.tsv`, with a
     `latest.tsv` symlink pointing at it. Tab-separated so it can be read with the tools already
     on the host and by the smoketests without adding a parser dependency. Header lines begin
     with a hash and carry `key=value` pairs: `snapshot`, `snapshot_epoch`, `replica_snapshot`,
     `replica_epoch`, `covered` (space-separated service names), `duration_seconds`,
     `written_bytes`, `usedbysnapshots_bytes`, and `status` (`ok` or `fail`). Body rows are six
     fields: kind, subject, check, result, bytes, hold_at — where kind is one of `dataset`,
     `sqlite`, `pgdump` or `replica`. Emit one `dataset` row per dataset walked, one `sqlite` row
     per database checked, one `pgdump` row per archive listed, and one `replica` row.

     The `hold_at` field carries the snapshot name that dataset's last-verified hold now sits on,
     and is a single dash on row kinds where it does not apply. It is what makes `latest.tsv`
     answer the question an operator actually asks under pressure — "which snapshot would a
     restore use, and is it known good?" — without reading pool state. On a night where a dataset
     failed, its `hold_at` shows the older snapshot the hold stayed on, which is precisely the
     snapshot to restore from.

     The two byte counters come from the dataset's written-since-newest-snapshot and
     used-by-snapshots properties; recording them every night converts the churn estimate into
     an observed series with no extra tooling. Note in a comment that the manifest necessarily
     rides the *next* snapshot rather than the one it describes, which is expected.
  9. **Write the metrics**, to `/persist/var/lib/node-exporter-textfile/backup.prom`

**ZFS holds**
A `last-verified` hold tag on each covered dataset, advanced by the nightly verification, as the very
     last action of the run. Emit `backup_last_snapshot_timestamp_seconds`,
     `backup_last_replica_timestamp_seconds`, `backup_last_verify_timestamp_seconds`,
     `backup_verified_files` labelled by kind and result,
     `backup_persist_written_bytes`, and `backup_persist_usedbysnapshots_bytes`, each with its
     help and type lines. Write to a temporary file in the same directory, set mode `0644`, then
     rename into place, so the collector can never read a half-written file. Being last is the
     point and must be commented: under strict error handling, a failure anywhere above means
     the stamp is never written, so a fresh timestamp cannot coexist with a failed run.
  10. **Compose one digest** and send it through the sendmail wrapper: the snapshot name, the
     counts by kind and result, the durations, the two byte counters, each dataset's hold
     position, and any failure lines. Paths, check names, results and sizes only — never file
     contents.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| snapshot tree → verification job | The job enumerates filenames it did not choose and opens files it did not write |
| verification job → metrics file → external scraper | A stamped timestamp is the only evidence an external observer has that the run happened |
| dump output → local filesystem | Portable archives of every database on the host land in a directory that did not previously exist |
| digest and failure mail → outbound mail | Job output leaves the host |
