  <action>
  Extend the restore tool from the tracer's copy-only scope to its full scope. The three-step
  shape does not change — stop the unit, replace the state, start the unit — and none of the
  existing guards may be weakened.

  Four additions:

  **Listing.** A flag that prints the snapshots available for a service, in creation order, with
  names, creation times and sizes, then exits without modifying anything. The snapshot listing is
  the restore-time picker, and the nightly manifest sits beside it supplying the verification
  evidence for each night. Mark the entry that the service's last-verified hold sits on, so the
  operator can see at a glance which of the listed snapshots is the proven-good one rather than
  cross-referencing the manifest by hand. Make the listing work for both sources, since the
  operator will want to know what the replica has when the source is the problem.

  **Default snapshot selection, and why it is now safe.** With no explicit snapshot given, the
  tool restores the last *verified* snapshot for that service — the one the manifest's hold field
  names — rather than merely the newest. Newest is the wrong default for a restore: the newest
  snapshot is the one most likely to contain whatever went wrong.

  That default now has an enforcement backstop rather than being a convention. The verification
  job places a hold on the snapshot it names, and a held snapshot cannot be destroyed, so the
  snapshot the default resolves to is guaranteed still to exist no matter how long ago it was
  taken or how much pruning has happened since. Before this, a default pointing at a manifest
  entry could resolve to a snapshot retention had already removed.

  Resolve the default from the manifest, then assert the resolved snapshot actually exists and is
  actually held before using it. If the manifest and the pool disagree, fail loudly and name both
  — that disagreement means either the manifest is stale or a hold was released by hand, and both
  are things the operator needs to know before restoring rather than after.

  **Source selection.** A flag choosing between the source pool's snapshots and the replica's,
  defaulting to the source. The replica dataset is deliberately not automatically mountable and is
  read-only, so reading from it requires mounting it explicitly first; do that inside the tool,
  and leave it in the state you found it. This is the path that matters when the source pool is
  the thing that failed, so it must work without the operator remembering a mount incantation.

  **Database restore.** A flag naming a database to restore from the portable archive that rode
  inside the chosen snapshot. Restore with a clean-first, tolerate-missing strategy so a repeated
  restore is not blocked by objects the previous attempt created. This is a flag on one tool, not
  a second tool: the state directory replacement and the database restore are two halves of the
  same operation for an application with both, and keeping them in one place is what makes the
  procedure identical for every service.

  **Gated rollback.** A flag selecting the fast destructive mechanism instead of the copy. Three
  guards, all mandatory: it requires the existing override flag to be present as well, so it can
  never be reached by a single flag; it is refused outright against the replica, because rolling
  the receive side back diverges it from the source and the next replication would silently
  repair that by discarding the operator's rollback; and the refusal messages name both the reason
  and the flag combination that would permit it. The reason copy remains the default deserves a
  comment where the flag is parsed: the destructive mechanism removes every snapshot newer than
  the target, which on a failed restore removes both the evidence and the retry options.

  **Preview.** A dry-run flag that resolves everything the real run would resolve — the chosen
  snapshot (and why: latest verified from the manifest, or the explicit override), the source
  path, the target path, the unit that would be stopped and started, whether the non-empty
  refusal or the move-aside would trigger and where the previous state would land — then prints
  those as the exact operations and exits 0 without performing any of them. It must compose with
  every mode: copy, replica source, database restore, and rollback (where it prints the snapshots
  that would be destroyed — the strongest argument for previewing). Resolution failures (unknown
  service, missing snapshot) still exit non-zero so a dry run is an honest rehearsal.

  Also add a usage message printed on an unrecognised flag or a missing service argument, since
  the tool now has enough surface that guessing is plausible. The usage output ends with worked
  examples (operator request): at least a listing invocation, a plain restore, and a dry-run
  restore, each with the real flag spellings.

  Keep the file clean under both the shell linter and the shell formatter, keep the tab
  indentation, and keep every path comparison behind a canonicalising resolution. Extend the
  packaging's runtime inputs with whatever the database restore needs.

  Extend the virtual machine behaviour test with the seven assertions listed above (numbered 20
  through 26, continuing from the nineteen the earlier plans established), driven from
  the covered-service set as the existing restore assertion is. Each must be red before it is
  green; record the observed red state per assertion.

  <name>Task 4: Write the runbook, then decide on deleting the migration's leftover state</name>
  <decision>Whether to permanently delete the fifteen old service state directories left under the persisted tree by the migration, now that the engine has completed a verified nightly cycle and three restores have been demonstrated.</decision>
  <context>
  The migration copied each service's state into its own dataset and deliberately left the
  original in place under the parent, untouched. That was the escape route: if a service had
  turned out unhealthy on its new dataset, the original was right there.

  It has now served its purpose. Every covered service has been healthy across a real reboot, a
  full nightly cycle has produced a verified manifest, and three restores have been executed. The
  leftovers now cost rather than protect: they roughly double the persisted footprint, they are
  captured by every one of the next thirty nightly snapshots, and they will mislead the next
  person who looks for a service's state directory.

  Deleting them is one-way in the sense that matters — but not absolutely. The state they hold is
  also inside every snapshot taken since the migration and inside the replica, so it is
  recoverable through the very mechanism this phase built. That is the honest framing: this is
  the first deletion whose safety net is the new engine rather than the old arrangement, which is
  exactly why it is a decision rather than a step.

  Before this decision is presented, the runbook must already be written and reviewed, because
  the runbook is the thing that makes the recovery path usable by a person under pressure.
  </context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| snapshot or replica → live service state | The restore tool writes across this boundary and the write is destructive to what was there |
| replica (read-only, unmounted) → restore read path | Reading from the replica requires temporarily changing its mount state |
| production snapshot data → scratch virtual machine | Real service state, including credentials embedded in it, leaves the host for the drill |
| runbook → future operator under pressure | A command in the runbook that does not work is discovered at the worst possible moment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-27 | Denial of Service | destructive rollback reached by accident | high | mitigate | The rollback path requires two flags rather than one, is refused outright against the replica, and its refusal messages name the exact combination that would permit it; two negative assertions in the virtual machine test cover both refusals |
| T-14-28 | Denial of Service | a restore discarding the state it replaces | high | mitigate | The tool moves the previous state aside under a dated name and never deletes it; each live drill spot-checks a file inside the preserved copy to prove it is a real copy rather than an empty directory |
| T-14-29 | Information Disclosure | production state copied into a scratch virtual machine | high | mitigate | The drill copies only the one service's state directory and the one database archive it needs, into a virtual machine on the operator's own workstation, which is destroyed after the drill; nothing is copied to a third party or a shared host |
| T-14-30 | Tampering | replica left mounted or writable after a restore read | medium | mitigate | The tool mounts the replica for the read and returns it to the state it found it in; a smoketest independently asserts the replica is unmounted, and the assertion runs after the drills |
| T-14-31 | Repudiation | a drill recorded as demonstrated without being executed | high | mitigate | Acceptance requires exact commands and observed output; a described procedure is explicitly disallowed as evidence, and the runbook's worked examples are the drill transcripts rather than invented ones |
| T-14-32 | Denial of Service | leftover state deleted before the replacement is proven | high | mitigate | The deletion is gated behind a decision checkpoint that cannot be reached until a full verified nightly cycle and three executed restores exist, and the runbook that makes recovery usable is written and reviewed first |
