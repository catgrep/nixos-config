  **The sixteen, and the rule that produces them.** The membership rule is mechanical rather

  A mechanical rule is the point. A curated list invites the question "why is this one in and
  that one out" at every future review, and answering it wrongly once produces a service nobody
  can restore individually. "Has a unit, has a dataset" needs no judgement and no maintenance
  argument.

  What stays in the parent is everything that is not one service's state: Samba, whose tdb files
  are written by several units and belong to none of them; the systemd and network state; the
  machine identity and host keys; the log tree; the dump and manifest directories this slice
  creates. The parent is the safety net, not a leftovers bin — its recursive snapshot covers
  every one of those paths and every path nobody thought to register. Say that in a comment above
  the set, because the reader's first question is what the rule excludes and why that is safe.

  **`hosts/ser8/backup/services.nix`**: add the fifteen new keys. Each value is
  `{ unit = "<unit>.service"; }`. Two of the sixteen have a unit name that is not derivable from
  the key, which is the entire reason this attribute exists: Home Assistant's key is `hass` and
  its unit is `home-assistant.service`, and Tailscale's key is `tailscale` while its unit is
  `tailscaled.service`. Read every unit name from the module that defines the service rather than
  deriving it, and confirm each one resolves by evaluating the systemd unit set afterwards — a
  key whose unit name is wrong produces a restore tool that stops nothing and starts nothing
  while reporting success.

  Note for the ordering that matters later: `postgresql` is in the set, and the applications
  whose data lives in it are too. Nothing about that is a problem for declaration, but record in
  a comment that a restore or migration touching both must stop the dependants before the
  database and start them after it.

  **`hosts/ser8/disko-config.nix`**: add one `"safe/persist/<name>"` block per new service beside
  the existing `"safe/persist/donetick"`, each `type = "zfs_fs"` with
  `options.mountpoint = "legacy"` and the disko-level `mountpoint = "/var/lib/<name>"`. The
  disko-level attribute is what generates the NixOS `fileSystems` entry; that is the whole
  mechanism, and no `fileSystems` entry should be hand-written anywhere for these paths.

  Two properties beyond the mountpoint, and no others:

  - **`atime = "off"` on every child.** The tracer's `donetick` already carries it; confirm that
    rather than re-adding it, and give the fifteen new children the same. Set it locally on each
    child rather than relying on it being inherited. The inherited value would be correct today,
    which is precisely the problem: an inherited property is an accident that happens to be
    right, and it silently becomes wrong the moment a parent property changes. A locally set
    value is a recorded intent. The reason it is off at all is that access-time updates turn
    every read into a write, and on a copy-on-write filesystem every write is a new record that
    the next snapshot then pins — so leaving it on would have the engine paying snapshot space
    for the act of reading.
  - **`recordsize = "16K"` on the `postgresql` child only.** The record is this filesystem's
    copy-on-write unit and therefore its snapshot-pinning unit: change one byte and the whole
    record is rewritten and the old one is held by every snapshot referencing it. The default is
    128K, so a single row update in an 8K database page pins 128K. At 16K it pins 16K, and 16K
    is chosen rather than 8K because it holds two compressed pages, which is the standard
    guidance for this database on this filesystem. The effect is on nightly snapshot deltas, not
    on throughput, which is why it earns its place in an otherwise untuned design.

  Every other child keeps the 128K default, deliberately, and that decision needs its own comment
  because the natural instinct after reading the database rationale is to tune the rest. Their
  content is mixed — a database sitting beside images, metadata trees and configuration — and 128K
  is the compromise those mixed workloads are designed around. Speculative per-dataset tuning is
  exactly the cleverness this slice is supposed to avoid. If a later churn measurement fingers a
  specific dataset, dropping that one is a one-line change made with evidence rather than a guess
  made now.

  Write both rationales as plain-language comments above the declarations, in the style the pool
  already uses for its own per-option reasoning. No planning terminology.

  **Where these properties get checked, and why not here.** The assertion in `datasets.nix`
  compares `fileSystems` device paths; it has no visibility into pool properties, because those
  are not part of the evaluated configuration — the declarations describe them but nothing at
  build time reads them back off a pool that does not exist yet. Do not stretch that assertion to
  cover properties. The property checks belong to the two layers that can see a real pool: the
  layout test in the next task, which asserts them against a pool built from these declarations,
  and the dataset-properties smoketest, which asserts them against the live host after the
  cutover. Note that split in a comment beside the assertion so the next reader does not add a
  property check where it cannot work.

| declaration → live pool | A declared dataset that was never created leaves the service writing into ephemeral storage that the boot-time rollback destroys |
| impermanence bind layer → dataset mount layer | Two mechanisms competing for the same path, with no ordering relationship between them |
