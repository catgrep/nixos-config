<objective>
Prove the backup architecture end to end on one service before any of it is built out.

One service's state travels the full path — child dataset, atomic recursive snapshot, replication
to the backup pool, restore back into the live path — and every step is asserted by a NixOS VM
test that runs under `nix build`, with no live ser8 mutation anywhere in this plan.

Purpose: three properties decide whether the whole design is viable, and all three are cheap to
test and expensive to discover late. Does a recursive snapshot really land parent and children in
one transaction group? Does an unprivileged receive into the backup pool work without shadowing
live mountpoints? Does a restore out of `.zfs/snapshot` actually reconstruct usable state? If any
answer is no, the architecture changes, and it should change after one commit rather than after
the dump engine, the verify walk, the metrics, and sixteen live migrations are already built on
it.

Output: the `hosts/ser8/backup/` slice with its covered-service set, snapshot/replication policy,
and restore tool; the repository's first `checks` flake output; and the VM behaviour test that
proves the slice works. The stale scaffolding this slice replaces is deleted in the same plan.

**Already done, do not repeat:** D-17's requirement amendments were discharged during planning,
not by an executor. `.planning/REQUIREMENTS.md` BKP-01 through BKP-07 were reworded on
2026-08-26 to describe the snapshot model — most importantly BKP-03, whose prohibition now names
the *non-atomic* live file copy as the forbidden mechanism and names the atomic snapshot plus a
snapshot-read structural check as the sanctioned one, and BKP-07, which is now whole-of-persist
coverage rather than a named application list. The roadmap's Phase 14 section was already
rewritten for the pivot before planning began and needs no further amendment beyond its plan
list. Read the amended wording as the current requirement text; do not re-amend it.

  Build the thinnest complete path through every layer this phase touches, wired end to end, for
  exactly one service — `donetick`. Donetick is the choice because it is the smallest live
  database on ser8 and is already locked as a restore-drill target, so the tracer's subject is
  the same subject the drills will use later. No other service is wired in this task; expansion
  to the remaining covered services is a later plan.

  Nothing in this task touches ser8. Every change is repository-only and every assertion runs in
  a VM. Datasets named here are declarations, not creations — activation never runs disko's
  create script, which is why the imperative creation is separately scheduled in a later plan.

  **Storage declarations** in `hosts/ser8/disko-config.nix`:
  - Add `"safe/persist/donetick"` beside the existing `"safe/persist"` block, `type = "zfs_fs"`,
    `options.mountpoint = "legacy"`, `options.atime = "off"`, and the disko-level
    `mountpoint = "/var/lib/donetick"`. The disko-level attribute is what generates the NixOS
    `fileSystems` entry; the `legacy` option value is what keeps ZFS from mounting it on import
    ahead of the mount ordering. Access-time updates are set off *locally on the child* rather
    than left to inherit, because an inherited value is an accident that happens to be right
    today and reverses silently when a parent property changes — and the reason it is off at all
    is that on a copy-on-write filesystem every read-triggered timestamp write becomes a new
    record the next snapshot pins, so leaving it on means paying snapshot space to read. Every
    later child carries the same property for the same reason.
  - Add `"persist-replica"` to the `backup` pool's `datasets`, with `mountpoint =
    "/mnt/backup-replica"`, `canmount = "noauto"`, `readonly = "on"`, and
    `"com.sun:auto-snapshot" = "false"`. Do not set `dedup`; the `backup` pool root already
    inherits it off, and a local property would obscure that.
  - Both declarations get a block comment above them, in the style of the existing `media` pool
    comment, stating in plain language why the replica must not be auto-mounted and why each
    child dataset exists. No planning terminology in any comment.

  **The covered-service set** in `hosts/ser8/backup/services.nix`: a plain Nix attrset
  file — not a module — returning one key per covered service. For this task the set contains
  only `donetick`. The key is simultaneously the state directory name under `/var/lib`, the
  child dataset name under `rpool/safe/persist`, and the restore tool's service argument, which
  is what makes it the single identifier for the whole slice. The only value that genuinely
  varies is the systemd unit, because a state directory name and its unit name are not always
  the same — Home Assistant's state lives at `/var/lib/hass` but its unit is
  `home-assistant.service`. So each value is exactly `{ unit = "<name>.service"; }` and nothing
  more. No modes, owners or groups: the existing tmpfiles rules and the service modules' own
  `StateDirectory` handling already own directory ownership, and duplicating those values here
  would create two sources of truth that can disagree.

  This file is imported with `import ./services.nix` by `datasets.nix` and
  `restore.nix`; it must NOT appear in `default.nix`'s `imports` list, because it is data and
  not a module.

  **`hosts/ser8/backup/datasets.nix`**: consumes the covered-service set and emits one
  `assertions` entry per service, asserting that `config.fileSystems."/var/lib/<svc>".device`
  equals `rpool/safe/persist/<svc>`. That assertion is the anti-drift link between the coverage
  set and the storage declarations: it makes a covered service without a matching declaration a
  build failure rather than a silent coverage hole. Give the assertion a message that names the
  missing declaration and the file it belongs in. This file emits no tmpfiles rules — existing
  ownership rules stay where they are.

  **`hosts/ser8/backup/policy.nix`**: `services.sanoid` and `services.syncoid`.
  - `services.sanoid.enable = true`, `interval = "hourly"`. Hourly is deliberate and needs a
    comment: the tool decides from pool state whether the nightly is due, so waking it often is
    what gives missed-run catch-up across the impermanence rollback, which does not preserve
    systemd timer stamps.
  - `templates.persist`: `autosnap = true`, `autoprune = true`, and every period stated
    explicitly — `frequently = 0`, `hourly = 0`, `daily = 30`, `weekly = 0`, `monthly = 0`,
    `yearly = 0` — plus `daily_hour = 3`, `daily_min = 0`, and `script_timeout = 0`. That last
    value disables the tool's own five-second hook deadline rather than imposing one, which is
    the direction every timeout decision in this engine goes: set no custom unit timeout tighter
    than the systemd default anywhere in the slice. A step that runs long is reported by the
    staleness alert, which is a signal; a step killed on a guessed deadline is a self-inflicted
    outage that looks like a real failure. Every
    period is stated because the module drops null keys from the generated file and the tool's
    own shipped defaults then apply; the comment must say that, because the values look
    redundant otherwise.
  - `datasets."rpool/safe/persist" = { use_template = [ "persist" ]; recursive = "zfs"; }`. The
    string value, not a boolean: it is what produces a single recursive snapshot call and hence
    one transaction group across parent and children.
  - `templates.replica`: `autosnap = false`, `autoprune = true`, `daily = 90`, every other
    period `0`. Ninety nights on the backup pool is the locked receive-side retention: the pool
    has over 21 T free and steady-state increments project in the tens of megabytes, so three
    months is a meaningful "we noticed late" window at single-digit gigabytes.
  - `datasets."backup/persist-replica" = { use_template = [ "replica" ]; recursive = "zfs"; }`.
  - `services.syncoid.enable = true`, `interval = "hourly"`, `commonArgs = [ "--no-sync-snap" ]`,
    and `commands."rpool/safe/persist" = { target = "backup/persist-replica"; recursive = true;
    recvOptions = "u x mountpoint"; extraArgs = [ "--create-bookmark" ]; }`. The `recvOptions`
    value carries two flags and both are load-bearing — one because the mount permission cannot
    be delegated on Linux so an unprivileged receive that tries to mount fails outright, the
    other because dataset properties travel in the send stream and an inherited service
    mountpoint on the replica is a loaded gun. Say both reasons in the comment.
  - This is a host slice, so assign directly; `lib.mkDefault` is a `modules/` idiom and is not
    used in `hosts/ser8/`.

  **`hosts/ser8/backup/restore/backup-restore`** (bash) and **`restore.nix`** (packaging):
  package with `pkgs.writeShellApplication`, `runtimeInputs = [ pkgs.zfs pkgs.coreutils
  pkgs.util-linux pkgs.systemd ]`, `text` prefixing an exported `BACKUP_COVERED_SERVICES` onto

  `BACKUP_COVERED_SERVICES` is a space-separated list of `name=unit` pairs built from the
  covered-service set — `donetick=donetick.service` for this task, growing to include
  `hass=home-assistant.service` when the set expands. One injected variable carries both the
  allowlist and the unit map, so the tool never guesses a unit name from a directory name.

  The script implements exactly three steps for every service — stop the unit, replace the state
  from the chosen snapshot, start the unit — and this task implements only the copy mechanism.
  Scope for this task: positional `<service>`, plus `--snapshot <name>` and `--force`. The
  `--list`, `--from replica`, `--rollback` and `--pg-database` flags are a later plan and must
  not be stubbed here; an unrecognised flag exits non-zero with a usage message.

  Required behaviour, in order:
  - `: "${BACKUP_COVERED_SERVICES:?}"` at the top so a mis-packaged tool fails loudly.
  - Reject a service name that is not the left-hand side of one of those `name=unit` pairs,
    before any dataset name is constructed, and resolve the unit from the matching right-hand
    side. Never interpolate an unvalidated name into a dataset path or a unit name.
  - Resolve the dataset as `rpool/safe/persist/<service>`, resolve its mountpoint with
    `zfs get -H -o value mountpoint`, and when that is the legacy sentinel resolve the real
    target with `findmnt -n -o TARGET -S <dataset>`.
  - Default the snapshot to the newest by creation when `--snapshot` is absent. Mark this in a
    comment as deliberately temporary: once the nightly verification exists it will place a hold
    on the last snapshot proven good per service, and the default becomes that snapshot instead,
    because the newest snapshot is the one most likely to contain whatever went wrong. Newest is
    the only defensible default while nothing has verified anything yet.
  - Fail loudly and
    name the dataset when the resolved snapshot directory does not exist.
  - Refuse a non-empty live target unless `--force` was passed. The refusal message names the
    path and names `--force` as the flag that would permit it, matching the existing
    "Refusing to ..." convention in the repo's other destructive script.
  - Move the previous live state aside under a dated suffix rather than deleting it, then
    recreate the directory and copy with `cp -a --reflink=auto` from the snapshot path.
  - Start the unit, assert it is active, and print both the snapshot restored from and the path
    the previous state was preserved at.
  - `set -euo pipefail`, an `ERR` trap that names the failed operation, `realpath -e --` before
    any path comparison, and tab indentation to match the repo's other shell scripts.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| rpool (live tree) → backup pool (replica tree) | Dataset properties travel inside the send stream, so a receive can import a mountpoint that points back at live service state |
| unprivileged replication user → ZFS delegation | Replication runs without root and needs temporarily delegated pool permissions for the duration of a run |
| snapshot tree → live state directory | The restore tool writes across this boundary into paths a running service owns |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-01 | Tampering | `backup/persist-replica` tree | high | mitigate | Receive with both the do-not-mount and mountpoint-exclusion options; `canmount=noauto` and `readonly=on` on the replica root; VM test asserts the replica is unmounted and that no replica mountpoint begins with `/var/lib` |
| T-14-02 | Denial of Service | snapshot pruning over `rpool/safe/persist` | critical | mitigate | The policy tool only considers snapshot names carrying its own automatic prefix and enforces a minimum-count floor before any destroy; the VM test asserts a differently-named anchor snapshot survives a prune run |
| T-14-03 | Denial of Service | `backup-restore` against live state | high | mitigate | Service name must be a member of the declared covered set before any dataset path is built; a non-empty target is refused without an explicit flag; prior state is moved aside under a dated name rather than deleted |
| T-14-04 | Elevation of Privilege | ZFS delegation residue on `rpool/safe/persist` | medium | mitigate | The replication module grants in `ExecStartPre` and revokes in `ExecStopPost`; the VM test asserts the delegation set is empty after a completed run |
| T-14-05 | Information Disclosure | snapshot tree readable by a local unprivileged user | medium | accept | Snapshot paths inherit the live directory modes, which are already the host's existing access-control decision; this plan introduces no relaxation of them |
| T-14-SC | Tampering | `sanoid`/`syncoid` package additions | high | mitigate | Both resolve from a locked flake input by content hash rather than a mutable name registry; the research Package Legitimacy Audit records no `[ASSUMED]` or `[SUS]` entries, so no install-time human gate applies |
</threat_model>
