<objective>
Make the declared storage real on the live host, move sixteen services onto their own datasets, and
activate the engine.

Purpose: this is the only plan in the phase that changes ser8. Everything before it was proven in
a virtual machine precisely so that this plan could be a sequence of individually approved,
individually verified steps rather than a discovery exercise. The ordering is load-bearing in one
specific way: the datasets must exist before the configuration is activated, because activation
generates mount entries for them and never creates them, and a mount entry pointing at a dataset
that does not exist is a failed boot.

each holding a verified copy of its service's state, the configuration activated and made the
boot default, and every covered service healthy across a real reboot.

  <decision>Whether to delete the 8.4 GB of Jellyfin activation tarballs on ser8 before the first replication run, permanently and without an archive copy.</decision>
  <context>
  Jellyfin has been writing a tar of its entire state, roughly 1.8 GB each time, on every
  activation — five landed on a single day in August. That directory is now 8.4 GB and it is the
  single largest source of change in the whole persisted tree: it accounts for roughly 9.0 GB of
  the 9.7 GB written since the last manual snapshot, meaning the genuine steady-state change rate
  is around 75 MB a day and everything above that is tarballs.

  The configuration change that stops new ones being written has already landed in the
  repository. This decision is only about the existing files.

  It matters now rather than later for two reasons. The first replication run has no incremental
  base and sends everything: with the tarballs it is roughly 11 GB, without them roughly 2.8 GB.
  And every one of the next thirty nightly snapshots would pin whatever is present when it is
  taken, so keeping them costs the space repeatedly rather than once.

  This is a one-way action. The tarballs are point-in-time copies of Jellyfin's configuration and
  database, and deleting them destroys those historical points permanently. What replaces that
  capability is the thing this whole phase builds: nightly snapshots of the same state with a
  thirty-night window, plus the system's own generations for configuration rollback. The
  replacement is strictly better, but it does not exist yet at the moment of deletion, which is
  the honest framing of the risk.
  </context>

  <action>
  Sixteen migrations, one service at a time, each individually approved with its exact commands
  shown first. The services are the sixteen keys of the covered-service set; take the list and the
  unit names from that file rather than from this plan, so a change made during planning cannot
  drift from what is executed. Two of the unit names are not derivable from the key, which is why
  the file is the authority and guessing is not permitted.

  The sequence deliberately differs from the obvious one in a way that matters. Do not stop a
  service, migrate it, and restart it onto a manually mounted dataset under the currently running
  configuration. That leaves the service running on a mount the active generation does not know
  about, for however long the remaining migrations take. Instead:

  **Phase A, for each service in turn:** stop the unit; create its dataset unmounted with the
  declared properties; verify those properties before writing anything into it; mount it
  temporarily at a scratch path; copy the state into it preserving everything, from the path under
  the persisted tree rather than from the live path; compare the copy against the source
  recursively and require the comparison to report no differences; unmount the scratch path. Leave
  the unit stopped and leave the original state exactly where it is. Do not delete or move the
  original.

  Creating unmounted is not stylistic — creation order is not mount order, and a dataset that
  mounts the instant it is created can shadow a path that something else is about to use.

  **Properties at creation, and why the order is not negotiable.** Every child is created with
  access-time updates off, and the database child is additionally created with a 16K record size.
  Set both with explicit options on the create command rather than leaving them to inherit, so the
  live pool records the same intent the declarations do and the properties read back as locally
  set.

  The record size in particular must be on the dataset *before the copy runs*, not added
  afterwards. Record size applies at write time and to newly written data only — setting it after
  the migration would leave every byte already copied at the 128K default and would produce a
  dataset that reports the right property while behaving like the wrong one. That is the worst
  outcome available here, because every check downstream would pass. So: create, read the
  properties back, and only then mount and copy. If a dataset is discovered to already exist
  without the property, do not patch it in place — destroy the empty dataset and recreate it,
  which is safe precisely because nothing has been copied into it yet.

  Do not add a record-size override to any other child. The rest keep the default deliberately,
  and a later change to one of them should come from a churn measurement rather than from
  symmetry with the database case.

  The comparison step is the gate. A copy that has not been compared is not a migration, and a
  service must not be started against a dataset whose contents have not been checked. If the
  comparison reports any difference, stop, report it, and do not proceed to the next service.

  **Stop order.** The database is in the covered set and so are the applications whose data lives
  in it. Stop the dependants before the database and do not start anything until the next task.
  Stopping the database first would leave four applications writing into a connection that has
  gone away, which is a messier state to copy than a cleanly stopped one even though the snapshot
  would survive it.

  **Phase B, once all sixteen have been copied and compared:** the services stay stopped and the
  activation in the next task performs the mount switch. That is the whole reason the copies are
  done with the services down and the originals untouched: at every instant either the old
  configuration is intact and correct, or the new one is, and never a hybrid.

  Record per service: the byte count and file count on both sides, the comparison result, and the
  wall-clock duration. Total moved is expected to be around 2.9 GB, dominated by one service's
  metadata tree with three more in the hundreds of megabytes and the rest small; if any single
  copy exceeds ten minutes, dispatch it as a detached unit with a job manifest and return rather
  than polling it.

  Mosquitto is the one service that is not a migration in the same sense: its state currently
  lives on the root filesystem that the boot-time rollback destroys every boot, so it has no copy
  under the persisted tree to migrate from. Copy from its live path instead, and note in the
  summary that this is the first time that state has had anywhere durable to live. The accepted
  consequence is that retained messages and session state now survive reboots, which is correct
  broker behaviour and is verified in the next task.

  Downtime for the covered services runs from the first stop in Phase A until the services come
  back in the next task, and it is now the whole application stack rather than a subset — media,
  household, automation and the database all together. Tell the operator the expected window
  before starting, name the services that will be down, and confirm they are ready for it. If the
  window is unacceptable, stop and report rather than improvising a partial migration: a subset
  migrated now and the rest later means two activations and two windows, which is a decision for
  the operator and not for the executor.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| planned configuration → running host | Activation applies mount entries generated from declarations that activation itself never created |
| old generation → new generation | Two configurations disagree about what mechanism owns each service state path |
| operator intent → destructive command | Every irreversible action on this host passes through an individual approval |

| T-14-22 | Denial of Service | service state loss during migration | critical | mitigate | The original state is never moved or deleted by this plan; the copy is compared recursively against the source and a difference halts the sequence; services stay stopped from copy until activation so no write lands on only one side |
| T-14-23 | Denial of Service | rollback anchor snapshot destroyed | critical | mitigate | The anchor's existence is confirmed before, between and after every step; the retention tool structurally cannot destroy it because its name does not carry the automatic prefix the tool matches on |
| T-14-24 | Tampering | replica dataset created without its safety properties | high | mitigate | Properties are read back individually after creation rather than inferred from the create command's success, and deduplication is confirmed to be inherited rather than set locally |
| T-14-25 | Denial of Service | first replication run colliding with the nightly upgrade window | medium | mitigate | The first run is deliberately not triggered in this plan; it is an out-of-band step in the next plan with its duration measured |
| T-14-26 | Information Disclosure | permanently deleting historical service state | high | mitigate | The only permanent deletion is gated behind an explicit decision checkpoint that states the one-way nature and the alternatives; all other removals in this plan have a live original |
| T-14-SC | Tampering | package additions reaching the running host | high | mitigate | The two new packages resolve from a locked flake input by content hash and were audited before adoption; activation installs exactly the closure that was dry-built and tested in a virtual machine |
